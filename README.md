## Working languages

**Six: Python, Node.js, Go, Rust, C++, Java.**

The point is not "write it six times." It is *see how the same idea looks
different depending on what the runtime does for you* — which is the whole
reason Layer 1's concurrency topic teaches more than any single-language
treatment of the same material could.

Not every topic gets all six. The rule is: **pick the languages that make the
mechanism visible**, and state a one-line reason in the topic README whenever
you use fewer. Silent omission reads as laziness; a stated reason reads as
judgement.

- **Where the runtime is the subject** — concurrency, scheduling, IO, memory,
  threading — use all six. That contrast *is* the lesson. Do not economise.
- **Where the mechanism lives outside the language** — Postgres isolation
  levels, query plans, cgroups, an HTTP protocol behaviour — fewer is
  correct. Six near-identical Postgres clients teach nothing.

What each one earns its place by showing:

- **Python** — the production stack. The GIL, asyncio, and what a managed
  interpreter hides from you.
- **Node.js** — single-threaded by design, plus libuv's hidden pool. The
  strictest version of "one blocking call freezes everything."
- **Go** — M:N scheduling, the netpoller, async preemption. Usually the
  language that *doesn't* have the problem, which is as instructive as the
  ones that do.
- **Rust** — compile-time enforcement. What the type system refuses to let
  you write, and what `unsafe` makes visible.
- **C++** — the same hazards as Rust with none of the guardrails, and the
  only language here that talks to the kernel with nothing in between.
- **Java** — JIT-compiled but managed and GC'd, plus virtual threads
  (Java 21) as a second real answer to goroutines.

**Separately, and do not conflate the two:** the languages actually deployed
at work are **Go, Python, and Node.js**, over Postgres/MySQL in Docker. That
is why Python anchors most topics and why production-shaped examples use
FastAPI. Rust, C++, and Java are here to teach mechanism, not to be shipped.

## The central discipline: predict, then record

Every experiment in every layer is built the same way, and the shape is
deliberate:

1. **Predict, in writing, before you run anything.** A number with a unit, a
   ratio, or an ordering. Not "it'll be slower." Write it in
   `PREDICTIONS.md` — one line, under a minute.
2. **Run it. Record the actual number.** In the topic's blank results table.
   The tables in this repo ship empty on purpose.
3. **Then — and this is the part that matters — check whether the experiment
   is broken before you conclude the prediction was wrong.**

Every experiment carries an explicit **"what would mean the experiment is
broken rather than the prediction wrong"** note. A benchmark that ran for
400 microseconds measured your scheduler, not your code. A load test driven
by fixed VUs self-throttles when the service slows and therefore cannot
reproduce queueing at all. A "no data race observed" result at `-O2` may be
the optimizer having deleted the loop. There are three outcomes, not two:
**hit**, **miss**, and **broken**. Broken counts as neither, and mistaking
broken for a result is exactly how Layer 1 went wrong.

There are no pre-filled "What I saw" tables anywhere in this lab, and none
will be added. A number in this repo is either one you measured on your own
machine or it does not exist.

## Layer 1 is unverified — read this before trusting it

`01-machine/` topics 1-6 were generated by an LLM from the roadmap HTML and
**never run**. A later review found four real defects. They are recorded as
misses in [`PREDICTIONS.md`](PREDICTIONS.md) and the material carries them
until a verification pass fixes them:

1. **The "What I saw" tables are fabricated.** Every topic reports specific
   benchmark numbers (ns/step, syscall costs, lost-update counts) that were
   never produced by running anything on this machine.
2. **A reported race result is measuring the compiler, not the race.** The
   C++/Rust "0 lost updates" figure in `04-races-and-atomicity` is the
   optimizer hoisting the increment out of the loop. Rebuilt at `-O0` the
   same code loses roughly 1.9 million updates. The experiment was broken and
   the broken output was published as a finding.
3. **The Go asynchronous-preemption experiment does not test preemption.**
   Its "call-free tight loop" calls `time.Now()` every iteration, so it has
   function-call boundaries throughout and would have yielded under the
   pre-1.14 scheduler too. It demonstrates nothing about async preemption.
4. **Much of the code is Linux-only and fails silently on macOS.** `sys/epoll.h`
   does not exist on Darwin; `/proc/self/limits` does not exist on Darwin.
   Topics 5 and 6 have therefore never executed on the machine they were
   written for.

A fifth, cosmetic issue: prose counts went stale ("two of the four
languages") when languages were added, which is a small thing that signals a
large one — nobody reread it.

`01-machine/07-inside-a-container/` is different. It was written later, with
real research, against verified 2026 sources, and it deliberately uses only
constructs that work inside Docker Desktop's linuxkit VM on macOS. Treat it
as trustworthy-pending-your-own-run, unlike its six siblings.

## The bar for an experiment

A topic's experiment is not finished until it hits as many of these as
honestly apply:

1. **Runnable under load.** A service in `docker compose` with an
   **open-loop** load generator. Closed-loop (fixed-VU) generators
   self-throttle when the service slows and cannot reproduce queueing,
   pool exhaustion, or metastable collapse — use k6's
   `constant-arrival-rate`/`ramping-arrival-rate` executors or
   `vegeta -rate`. This trap is flagged in four separate layers because it is
   the single most likely way to get a null result and draw the wrong
   conclusion.
2. **Lift-to-work patterns.** The fix should be code you could paste into a
   real PR: timeout budgets, retry with full jitter and a retry *budget*,
   circuit breakers, idempotency keys, the transactional outbox.
3. **Incident replay.** Reproduce a specific named production failure end to
   end — connection pool exhaustion, CFS CPU throttling, a metastable retry
   storm, replica lag serving stale reads — then fix it and prove the fix.
4. **Prediction logged first.**

## Environment

Everything is designed to run on **macOS with Docker Desktop** (linuxkit VM,
cgroup v2). Where a technique is Linux-host-only — `nsenter` into a
container's netns, container-level clock skew via time namespaces, GPU
passthrough — the affected layer says so up front and specifies a portable
alternative (a `network_mode: "service:api"` sidecar, an app-level
`CLOCK_OFFSET_MS` hook, a host-side model server). This is a direct response
to Layer 1's defect #3.

Give the Docker Desktop VM **at least 4 CPUs**, or the host-cores-vs-cgroup-quota
gap that half of `01-machine/07` depends on is unobservable.
